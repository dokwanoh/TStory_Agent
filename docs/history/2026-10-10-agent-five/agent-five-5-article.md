# Claude가 ‘AI 팀’의 일 순서를 짠다 🧩 여러 에이전트, 언제 도움이 될까요?

AI에게 문서가 많은 일을 맡길 때는 답변 하나보다 ‘누가 무엇을 읽고, 누가 다시 검토했는지’가 중요해져요. Claude가 여러 AI의 작업 순서를 프로그램으로 실행하는 기능을 내놓았습니다. 개발자용 베타가 무엇을 바꾸는지, 우리 일에 필요한지 쉽게 살펴볼게요.

## 30초 요약 ⏱️

| 궁금한 점 | 짧은 답 |
|---|---|
| 무엇이 새롭나요? | AI가 작업 프로그램을 만들고 여러 에이전트의 결과를 합칩니다. |
| 바로 쓸 수 있나요? | Claude Managed Agents API 베타입니다. 일반 채팅의 새 버튼이 아니에요. |
| 언제 검토할까요? | 독립적으로 나눌 문서가 많고 검토 기준을 정할 수 있을 때요. |
| 무엇을 확인하나요? | 누락·실패 자료, 출처와 최종 결과예요. |

공식 발표 날짜는 2026년 10월 9일입니다. 정확한 발표 시각은 확인하지 못해 조사 시점 기준 24시간 이내인지 단정하지 않습니다.

## 1. AI 한 명을 더 똑똑하게 만드는 변화일까요? 🧩

이번에는 일을 나누고 이어가는 방식이 바뀌었어요. Anthropic은 공식 업데이트에서 ‘dynamic workflows’를 베타로 발표했습니다. 여기서 workflow는 일을 진행하는 순서이고, 에이전트는 자료를 읽거나 도구를 써서 맡은 일을 수행하는 AI예요.

쉽게 말하면 Claude가 ‘자료별로 분석하기 → 분석을 모아 검토하기 → 답변 만들기’를 실행할 프로그램을 작성하는 방식입니다. 서버가 그 프로그램을 뒤에서 실행하면서 여러 에이전트의 결과를 연결해요.

여러 작업자를 따로 호출하는 것과 어떤 차이가 있을까요? 프로그램이 다음 단계를 정하고 결과를 전달하므로, 중심 AI가 매번 모든 작업자의 보고를 받아 다음 일을 지시하는 부담을 줄이는 구조입니다. **새 기능의 핵심은 AI의 숫자보다 일을 나누고 합치는 순서예요.**

다만 Claude Managed Agents는 개발자가 AI 작업 서비스를 구성하는 API입니다. API는 다른 프로그램이 서비스를 이용하게 하는 연결 방식이에요. 이 발표만 보고 일반 Claude 구독이나 Claude Code에 같은 기능이 자동으로 생겼다고 이해하면 안 됩니다.

공식 문서는 많은 문서를 검토하거나 큰 작업을 나누는 활용을 설명합니다. 그래서 이 소식은 작은 오류 수정과 성격이 달라요. AI에게 한 번 답을 받는 방식에서 여러 작업의 진행과 결과를 관리하는 방식으로 관심이 옮겨갈 수 있다는 점은 제 해석입니다. 이용자 수나 생산성 향상을 확인한 결과는 아니에요.

## 2. 문서가 많을 때는 이렇게 요청을 나눠요 📂

가정 예시로, 작은 개발팀이 프로그램을 바꾸기 전에 설치 안내와 변경 기록을 비교한다고 해볼게요. 아래는 실제 실행 결과가 아니라 요청을 설계하는 예시입니다. 문서 두 묶음은 설명을 위해 정한 것이며 서비스의 최소·최대 작업자 수를 뜻하지 않습니다.

원문 자료는 ‘현재 설치 안내 A’와 ‘새 버전 변경 기록 B’입니다. 요청은 “A의 설치 조건과 B의 변경 내용을 각각 읽고, 출처 위치를 붙여 주세요. 두 자료를 모두 다시 대조해 충돌하는 조건과 읽지 못한 자료를 구분해 주세요”처럼 쓸 수 있어요.

먼저 서로 독립적인 A와 B 분석을 나눕니다. 다음 검토 단계에서는 앞선 요약만 믿지 말고 원문 두 자료 전체를 대조하도록 요청해요. 마지막에는 ‘바뀐 조건·그대로인 조건·확인할 부분·처리 실패 자료’를 나눠 받는 식입니다.

예시 결과의 모양은 “A에서는 설정 항목이 이렇게 적혀 있고, B에서는 이렇게 변경됐다고 설명한다”는 비교표예요. 실제 설정 이름이나 값을 여기서 만들어 넣지 않는 이유는 제공된 원문 없이 정답처럼 보이는 내용을 만들지 않기 위해서입니다.

**결과를 볼 때는 문장이 매끄러운지보다 모든 자료를 다뤘는지 먼저 보세요.** 자료 목록과 결과 목록을 맞춰보면 한 묶음이 빠졌는지 알 수 있습니다. 출처 위치를 함께 받으면 요약이 원문과 다른 부분도 찾기 쉬워져요.

틀린 결과를 줄이려면 요청에도 실패 처리 기준을 넣는 편이 좋아요. 예를 들면 “열지 못한 문서는 추측하지 말고 이름을 적어 주세요. 조건이 충돌하면 하나로 합치지 말고 양쪽 내용을 남겨 주세요”입니다. 이는 요청 예시이며 자동으로 지켜진다는 보장은 아닙니다.

공식 문서에서도 workflow 실행이 완료됐다는 상태와 각 작업의 성공을 구분합니다. 따라서 ‘끝났다’는 표시만 보고 모든 문서가 검토됐다고 판단하면 안 돼요. 실패나 누락을 결과에 남겨야 사용자가 판단할 수 있습니다.

## 3. 많이 맡길수록 좋은 것은 아니에요 🧭

독립적으로 읽을 자료가 많고 같은 기준으로 결과를 비교할 수 있다면 이런 구조를 검토할 만합니다. 반대로 짧은 문서 하나를 요약하거나 서로 얽힌 내용을 계속 대화하며 고치는 일이라면, 작업자를 늘리는 비용과 관리가 더해질 수 있어요.

비용을 이해할 때는 ‘토큰’부터 알아두면 편합니다. 토큰은 AI가 입력과 출력을 처리할 때 세는 단위예요. 여러 에이전트가 각각 자료를 읽고 답하면 각자의 토큰 사용이 생깁니다. 단순히 여러 명에게 나눴다는 이유로 무료가 되거나 더 빠르고 정확해지는 것은 아닙니다.

문서 공유 범위도 생각해야 합니다. 작업자마다 대화 기록은 따로 있지만 같은 실행 공간의 파일을 공유해요. 대화를 나눈다고 자료 접근이 자동으로 분리된다는 뜻은 아니에요. 업무 자료를 넣기 전 허용할 자료와 도구의 범위를 정하는 이유입니다.

수정 요청 방식에도 차이가 있습니다. workflow 안의 작업자에게 일반 대화처럼 계속 후속 메시지를 보낼 수는 없어요. 각 작업의 결과는 프로그램이 받고 다음 단계에 사용합니다. 따라서 처음 요청에 검토 기준과 실패 목록을 정하는 일이 중요해집니다.

**도입을 판단할 질문은 ‘AI 몇 명을 쓸까’보다 ‘나눌 일과 합격 기준이 분명한가’예요.** 코드를 모르는 독자도 이 기준으로 팀의 도입 설명을 읽을 수 있습니다. 실행 상태뿐 아니라 실제 결과를 확인해야 하는 이유도 이해할 수 있고요.

오늘 해볼 행동은 실제 개인정보나 회사 기밀을 넣는 대신, 공개된 설치 안내와 변경 기록 두 개로 요청서를 써보는 것입니다. 입력 목록, 비교할 조건, 실패 표시, 내가 최종 확인할 부분을 적어보세요. API를 도입하기 전에도 일을 나눌 가치가 있는지 생각하는 데 도움이 됩니다.
