# AI에게 같은 일을 또 맡긴다면? 📝 Kiro Workflows, 단계와 멈출 조건을 저장해요

AI에게 수정·검토·재수정을 매번 따로 부탁하고 있다면, 잘된 작업의 단계와 완료 조건을 함께 남겨 보세요. Kiro Workflows는 그 흐름을 다시 쓰는 기능이지만, 실행이 끝났다는 말과 요구한 결과가 검증됐다는 말은 구분해야 합니다.

## 30초 요약 ⏱️

| 구분 | 알아둘 내용 |
|---|---|
| 저장 대상 | 담당 단계·순서·출력·반복 조건을 레시피로 남겨요. |
| 실행 방식 | 단계마다 별도 세션에서 작업하고, 병렬·반복도 구성해요. |
| 시작 조건 | 설정에서 활성화하며, IDE에서는 새 채팅을 시작해요. |
| 완료 판단 | 승인·검증 결과를 보고, 상한까지 실패하면 중단해요. |

2026년 9월 30일 공식 발표를 바탕으로 재사용 방법을 설명합니다. 본문의 최대 3회는 공식 예시 레시피의 설정이며, 모든 작업에 자동 적용되는 공통 규칙은 아닙니다.

## 1. 이전 답변보다 ‘잘된 순서’를 남겨요 🧩

워크플로는 일을 진행하는 흐름이에요. 요청을 정리하고, 구현하고, 검토한 다음 필요한 부분을 고치는 순서를 떠올리면 됩니다. 레시피는 그 흐름을 저장해 다시 실행할 수 있게 만든 설명입니다.

Kiro에서는 모델이 담당 Agent와 작업 순서를 정하고, 실행 환경이 계획에 따라 단계를 진행합니다. Agent는 맡은 일을 수행하는 AI 작업자라고 이해하면 돼요. 순서대로 실행하기, 반복하기, 나란히 진행하기를 조합할 수 있습니다.

각 단계는 별도의 세션과 새 문맥에서 실행됩니다. 문맥은 그 세션에서 모델이 참고하는 대화와 작업 정보예요. 검토 단계가 구현 담당자의 모든 생각을 그대로 이어받는 방식과 구별됩니다.

단계가 나뉘어도 앞 단계의 결과는 다음 작업에 전달해야 합니다. 공식 예시는 계획 파일과 검토 결과 파일처럼 출력물을 참조해 연결합니다. 누가 무엇을 만들고 다음 단계가 무엇을 읽는지 알 수 있는 구조예요.

**재사용할 것은 성공한 답변 한 문장보다, 결과를 확인한 작업의 순서와 조건이에요.** 같은 ‘끝났습니다’라는 답변을 받아도 파일이 바뀌었는지, 요청한 동작을 검증했는지는 다를 수 있습니다.

가정으로 메모 앱의 검색 기능을 추가한다고 해볼게요. 원래 요청은 ‘메모에서 단어를 찾아 결과를 보여 줘’입니다. 이 문장만 저장하기보다 대소문자 처리, 결과가 없을 때의 표시처럼 원하는 조건도 함께 적을 수 있어요.

후속 요청의 예시는 ‘요구사항 정리 → 구현 → 별도 검토 → 필요한 수정 → 처음 요구사항과 대조하는 흐름을 만들고, 각 단계의 결과를 남겨 줘’입니다. 직접 실행한 결과가 아닌 설명용 가정이며, 실제 단계와 검토 범위는 작업에 맞춰 정합니다.

## 2. 반복 횟수와 ‘끝났다’는 기준을 같이 정해요 🔁

공식 발표의 예시에는 설계 검토와 코드 검토의 반복이 있습니다. 각 반복은 최대 3번 안에 승인을 얻도록 설정돼 있고, 끝내 승인받지 못하면 해당 실행을 중단합니다. 마지막에는 최초 요구사항과 결과를 대조해 검증해요.

여기서 3은 이 예시가 정한 상한입니다. 모든 Kiro 작업이 무조건 세 번 시도한다거나 세 번이면 성공한다는 뜻은 아니에요. 반복 횟수만 보고 결과까지 보장된 것으로 읽으면 조건이 바뀝니다.

승인 조건은 다음 단계로 넘어가도 되는지를 판단하는 기준입니다. 예시 레시피는 검토 결과 파일의 승인 값을 읽습니다. 반복할 일과 멈출 조건이 함께 있어야 ‘수정 중’과 ‘완료’를 나눌 수 있어요.

**정해진 횟수를 다 썼다는 것은 성공의 증거가 아니에요.** 상한에 도달해 중단했다면 해결하지 못한 검토 사항을 남기고, 사람이 요구사항이나 접근 방법을 다시 살필 수 있어야 합니다.

메모 검색의 가정으로 돌아가 볼까요. 검토가 ‘검색어가 없을 때의 결과 표시가 빠졌다’고 했다면, 수정 단계가 그 항목을 처리한 뒤 다시 검토하도록 연결합니다. 확인할 차이는 수정했다고 말했는지가 아니라 원래 조건에 맞는 근거가 생겼는지예요.

서로 독립적인 검토는 병렬로 진행할 수 있습니다. 병렬은 여러 일을 나란히 실행한다는 뜻이에요. 공식 예시에서는 두 검토 결과를 모두 기다리고 모아 다음 판단에 사용합니다. 먼저 끝난 하나만 보고 전체 승인을 가정하지 않습니다.

Kiro는 실행 중 발견한 내용에 따라 흐름을 조정할 수도 있어요. 변경은 단계 사이에 적용되고, 이미 끝난 작업과 진행 중인 단계는 그대로 둔다고 설명합니다. 현재 단계를 소급해 새 규칙으로 완료한 것처럼 쓰는 기능은 아닙니다.

사용자가 만든 레시피는 JSON으로 저장할 수 있고 YAML도 지원합니다. 둘 다 구조화된 설정을 적는 형식이에요. 직접 형식을 외우기 전에 Kiro에게 흐름을 만들어 달라고 요청하고, 순서·출력·멈출 조건을 읽는 방법으로 접근할 수 있습니다.

## 3. 저장한 흐름도 처음에는 작게 실행해요 🌱

Workflows는 IDE·CLI·Web에서 제공한다고 발표했습니다. IDE는 코드를 편집하는 개발 도구, CLI는 명령어를 입력하는 실행 환경입니다. 세 환경은 같은 실행 기반을 사용하지만, 필요한 도구와 작업 권한은 내 환경에서 따로 살펴야 해요.

기능은 선택해서 켜는 방식으로 시작합니다. IDE에서는 프로젝트의 Workspace Configuration에서 Workflows를 활성화하고 새 채팅을 시작해야 합니다. 설정에 항목이 없다면 해당 계정에 아직 제공되지 않은 경우라고 안내해요.

Web의 클라우드 설정에는 선호하는 레시피를 저장해 프로젝트나 기기에서 다시 쓸 수 있습니다. 저장됐다는 사실은 다음 작업에서도 같은 입력·도구·권한이 모두 준비됐다는 보장은 아니에요. 실행할 환경에 맞는 흐름인지부터 읽어보세요.

작업은 백그라운드에서 진행되어 주 대화를 계속할 수 있고, 단계별 세션을 멈추거나 재개하며 방향을 조정할 수 있습니다. 끝난 뒤에도 해당 세션에 후속 질문을 할 수 있어요. 진행 보고와 실제 출력물을 함께 보는 데 쓸 수 있습니다.

**다시 쓸 흐름에는 사람이 판단할 지점도 남겨 두세요.** 공식 설명의 읽기 전용 조사 레시피처럼 작은 확인 작업으로 시작하면, 내용을 바꾸는 작업과 살펴보기만 하는 작업을 구분하기 쉽습니다.

비용은 기존 Kiro의 크레딧 모델을 따릅니다. 크레딧은 Agent 작업의 사용량을 계산하는 단위예요. 복잡한 흐름은 더 많은 작업을 실행해 사용량이 늘 수 있다고 설명하며, 단계가 많다고 무조건 더 싸거나 빠르다고 볼 근거는 없습니다.

반복되는 앱 수정과 검토를 수행하며 이미 확인된 절차가 있는 경우에 써볼 만합니다. 요구사항이 계속 바뀌거나 결과를 판단할 기준이 없다면, 먼저 작은 작업의 입력·출력·성공 조건을 정리하는 편이 도움이 돼요.

오늘 할 일은 최근 잘된 작업 하나에서 ‘입력 / 단계별 출력 / 완료 증거 / 실패 때 멈출 조건’을 적는 것입니다. 그 기록으로 다음 흐름을 만들되, 중단된 실행을 성공 기록으로 재사용하지 않는 것이 핵심이에요.
