# AI가 만든 코드에 비밀키가 섞였다면? 🔐 GitHub 새 탐지, 삭제만으로 끝나지 않아요

AI에게 앱을 만들게 한 뒤 GitHub에 올릴 생각이라면, 코드가 작동하는지와 함께 비밀키가 들어 있지 않은지도 살펴보세요. GitHub의 새 탐지 발표에서 중요한 것은 ‘찾기·올리기 전 차단·유출 뒤 대응’을 구분하는 일이에요.

## 30초 요약 ⏱️

| 구분 | 알아둘 내용 |
| --- | --- |
| 새 모델 | 주변 코드의 맥락으로 비밀정보 후보를 찾아요. |
| 현재 적용 | 기존 AI Password 알림 고객은 새 모델로 전환돼요. |
| 추가 검사 | AI 업로드 차단은 제한 미리보기, Copilot 새 검사는 예고 단계예요. |
| 이미 유출 | 파일 삭제만으로 끝내지 말고 키 폐기·교체부터 판단해요. |

발표일은 2026년 10월 7일입니다. 기존 알림의 변경과 앞으로 도입할 검사는 적용 시점·이용 조건이 달라요. 모든 계정에 새 기능이 열렸다는 뜻은 아닙니다.

## 1. 비밀키를 ‘코드처럼’ 올리면 왜 곤란할까요? 🔑

API 키는 프로그램이 다른 서비스에 접근할 때 쓰는 비밀 값이에요. 비밀번호나 접근 토큰도 비슷한 역할을 합니다. 토큰은 여기서는 AI가 세는 글 조각이 아니라, 서비스 접근에 쓰는 인증 정보라는 뜻이에요.

AI가 만든 파일에 이런 값이 섞였는지는 따로 봐야 합니다. 앱 화면이 잘 보이거나 요청한 기능이 동작한다는 사실만으로, 올려도 되는 내용까지 확인됐다고 판단하기는 어렵겠죠.

GitHub가 소개한 전용 모델은 앞뒤 코드를 살펴 비밀정보로 의심되는 값을 찾습니다. 정해진 형태가 없는 비밀번호도 대상에 포함해요. 코드를 새로 쓰거나 해설을 생성하는 모델과 역할이 다릅니다.

여기서 ‘탐지’는 의심되는 내용을 알려 주는 일이에요. 안내를 읽고 실제 인증 정보인지 판단하는 과정이 필요합니다. 이 발표를 모든 키를 빠짐없이 찾는다는 성능 보장으로 읽어서는 안 됩니다.

**작동하는 앱과 공개해도 되는 코드는 서로 다른 확인 항목이에요.** AI의 완료 보고에서 기능 확인만 읽었다면, 비밀 값이 있는지 살핀 범위도 물어볼 수 있습니다.

가정으로 AI에게 작은 메모 앱을 부탁했다고 해볼게요. 원래 요청은 ‘메모를 저장하는 예제를 만들어 줘’이고, 결과 파일에 외부 서비스 설정이 들어 있다고 합시다. 직접 실행한 사용 결과가 아닌 설명용 상황입니다.

이때 후속 요청은 ‘변경한 파일에 실제 비밀번호나 API 키가 포함됐는지 살펴보고, 의심되는 위치만 알려 줘. 비밀 값 자체는 답변에 복사하지 마’처럼 적을 수 있어요. 확인할 차이는 앱의 생김새가 아니라, 실제 인증 정보가 파일에 들어갔는지입니다.

## 2. 저장과 전송을 구분하면 검사 위치가 보여요 📤

커밋은 내 변경 사항을 버전 기록으로 남기는 일, 푸시는 그 기록을 원격 저장소로 보내는 일이에요. 저장소는 코드와 변경 이력을 모아 둔 공간이라고 이해하면 됩니다.

파일에서 키를 지웠더라도, 이전 커밋에 값이 들어 있다면 현재 파일과 과거 이력은 상태가 다를 수 있어요. 그래서 ‘지금 화면에 안 보인다’와 ‘기록에도 없다’를 같은 말로 쓰지 않는 것이 중요합니다.

새 발표에는 서로 다른 검사 경로가 담겼습니다. 기존 AI Password 알림 고객은 전용 모델로 자동 전환되고, GHSP·GHAS 고객의 AI 탐지 알림에는 추가 요금이 붙지 않는다고 안내해요. 두 약어는 GitHub의 보안 상품 이름입니다.

AI push protection은 원격 전송 시점에 비정형 인증 정보를 검사하는 기능으로, 발표 당시 제한된 이용자 대상 미리보기였어요. 대상은 GHSP 또는 GHAS를 구매한 GitHub Team·Enterprise Cloud 고객이며, 관리자가 활성화해야 합니다. 전송 전에 막는 기능이 이미 만들어진 내 컴퓨터의 커밋 이력까지 없애 주는 것은 아닙니다.

Copilot의 /security-review는 지원되는 CLI·앱 세션에서 취약점을 살피는 읽기 전용 검토 명령입니다. CLI는 명령어를 입력하는 실행 환경이에요. 새 비밀정보 분류기 검사를 여기에 더하는 일은 제한 미리보기 도입 예고로 구분해야 합니다.

**검토 명령을 실행한다고 새 유료 검사가 자동으로 켜지는 것은 아니에요.** 새 검사는 기본적으로 꺼져 있으며, 허용된 계정·정책에서 별도로 참여해야 합니다. 기존 검토의 사용량과 추가 검사의 비용도 구분해서 봐야 해요.

AI Credits는 GitHub의 AI 기능 사용량을 계산하는 단위입니다. 새 선택형 검사에는 향후 이 크레딧 사용이 적용된다고 예고했어요. ‘기존 알림 추가 요금 없음’을 ‘새 검사도 전부 무료’로 확대하면 조건이 달라집니다.

처음 쓰는 분이라면 기능 이름보다 내 계정에서 무엇이 열려 있는지, 누가 활성화할 수 있는지, 어떤 계정에 비용이 잡히는지부터 읽어보세요. 팀 기능이라면 관리자에게 확인할 내용도 여기에 포함됩니다.

[Copilot 읽기 전용 검토 역할 확인하기](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-custom-agents#built-in-agents)

## 3. 이미 올렸다면 ‘지우기’ 다음이 남아 있어요 🛑

GitHub의 유출 대응 안내는 비밀 값이 노출됐다면 이미 손상된 것으로 보고 대응하라고 설명합니다. 파일을 지우거나 새 커밋을 보내고, 저장소를 다시 만드는 것만으로 그 값의 악용을 막지는 못해요.

먼저 어떤 서비스의 키인지, 어디에 노출됐는지, 누가 관리하는지 파악합니다. 실제로 사용하는 앱이 연결돼 있는지도 봐야 합니다. 키를 폐기하면 그 키를 쓰는 서비스가 영향을 받을 수 있기 때문이에요.

폐기는 기존 인증 정보를 더 이상 못 쓰게 하는 것, 교체는 새 인증 정보로 바꾸는 일입니다. 공개된 활성 키나 운영용 인증 정보는 즉시 폐기를 우선합니다. 서비스 중단이 우려되면 책임자가 새 키 적용 후 기존 키를 폐기하는 순서를 정할 수 있어요.

앞의 가정에서 실제 키가 이미 원격에 올라갔다면, ‘AI에게 설정 줄을 지우라고 했으니 끝’이라고 볼 수 없겠죠. 기존 키를 계속 사용할 수 있는지, 필요한 교체가 이뤄졌는지, 관련 이력이 남아 있는지를 각각 확인하는 상황입니다.

**코드를 지우는 일과 노출된 키를 못 쓰게 하는 일은 별개입니다.** AI에게 맡길 때도 읽기 전용 점검과 실제 키 변경·폐기 권한을 구분하면 다음 행동을 정하기 쉬워요.

AI로 작은 프로젝트를 만들고 GitHub에 올리려는 분에게는 커밋 전 점검·전송 전 보호·유출 대응을 나눠 보는 방법이 유용합니다. 이미 운영 서비스의 키가 노출됐다면 혼자 파일만 수정하기보다 해당 서비스 담당자와 보안 책임자의 대응이 필요한 경우예요.

오늘 할 일은 최근 변경 파일 하나를 두고 ‘실제 인증 정보 포함 여부 / 커밋 여부 / 원격 전송 여부’를 나누어 적어보는 것입니다. 확인하지 않은 항목은 미확인으로 남겨 두세요. 경고가 없다는 말만으로 모든 위험이 없다고 결론 낼 필요는 없습니다.
