# AI가 고쳤다는 코드, 어떤 버전을 봤을까? 🔎 OpenHands의 이슈→PR 흐름

AI가 오류를 고쳤다고 말할 때는 ‘무엇이 고쳐져야 했는지’와 ‘어떤 버전을 검토했는지’를 함께 보면 좋아요. OpenHands Agent Canvas의 업데이트 정리는 요청을 구체화하고 수정본을 넘겨 검토하는 흐름이 왜 필요한지 보여 줍니다.

## 30초 요약 ⏱️

| 확인할 지점 | 뜻 |
|---|---|
| 이슈 | 해결할 문제와 원하는 결과를 적는 요청이에요. |
| 인수 조건 | 무엇이 충족돼야 완료로 볼지 정한 기준이에요. |
| PR | 수정 내용을 기존 프로젝트에 합치자고 제안하는 창구예요. |
| 현재 커밋 | 지금 검토할 코드 버전을 가리키는 기록이에요. |

공식 글은 2026년 10월 7일에 올라온 9월 업데이트 정리입니다. v1.17~v1.24의 8회 릴리스를 다루며, 모든 기능이 10월 7일 하루에 처음 나온 것은 아니에요.

## 1. ‘고쳐 줘’가 ‘완료 기준’으로 바뀌는 단계 📝

개발 작업에서 이슈는 해결할 문제를 기록한 항목입니다. 단순한 불만 한 줄로 시작할 수도 있지만, 원하는 결과가 드러나야 수정한 사람이 같은 목표를 보고 일하기 쉬워요.

Agent Canvas의 공식 정리는 이슈를 살피고 인수 조건을 정리하는 단계, 준비된 이슈를 수정본으로 만드는 단계, 검토와 유지 관리자의 다음 행동으로 연결하는 흐름을 설명합니다.

인수 조건은 낯설게 들리지만 ‘이것이 되면 고쳤다고 보자’는 기준이에요. 버튼 문구를 바꾸는 일이라면 바꿀 문구와 유지할 동작이 기준이 될 수 있습니다.

가정으로 ‘버튼을 눌렀는데 반응이 헷갈려요’라는 요청을 봅시다. 이 문장만으로는 누르는 동작이 실패하는지, 결과가 보이지 않는지, 문구가 모호한지 구분하기 어렵겠죠.

요청을 ‘버튼을 한 번 누르면 결과가 한 번 표시되게 해 줘. 안내 문구와 클릭 처리만 확인하고 로그인·결제 부분은 바꾸지 마’로 구체화할 수 있어요. 예시 결과는 그 범위에 해당하는 수정안과 확인 내용입니다. 직접 실행한 결과는 아닙니다.

**수정 전에 완료 기준을 함께 적으면 결과를 비교하기 쉬워집니다.** ‘일단 좋아 보인다’보다 ‘한 번 클릭·한 번 표시·다른 영역 유지’처럼 비교할 항목이 있는 편이 판단을 돕습니다.

초보자라면 어려운 구현 방법까지 미리 지정할 필요는 없어요. 현재 보이는 문제와 원하는 결과, 바꾸지 않았으면 하는 범위를 알기 쉽게 적는 것부터 시작하면 됩니다.

## 2. 검토한 코드와 지금 코드가 같은지 보세요 🔖

PR은 Pull Request의 약자로, 수정한 내용을 프로젝트에 합치자고 제안하는 단위입니다. 코드 차이와 의견을 한곳에서 보고, 프로젝트 담당자가 받아들일지 결정하는 데 사용해요.

커밋은 변경 사항을 남긴 버전 기록입니다. PR의 head commit은 그 수정 제안이 현재 가리키는 가장 앞선 버전이라고 이해하면 됩니다. 읽기 쉬운 별명과 별도로 버전을 구분하는 식별자가 있어요.

공식 업데이트 정리는 리뷰 에이전트를 시작하기 전에 PR의 정확한 head commit을 검사하는 흐름을 설명합니다. 예전에 봤던 수정본과 현재 수정본을 혼동하지 않도록 만드는 지점이죠.

가정으로 검토한 버전을 A, 이후 고친 버전을 B라고 부를게요. 실제 커밋 식별자를 대신한 설명용 이름입니다. A에서 버튼 문제가 해결됐더라도, B에 추가 변경이 들어갔다면 A의 확인 내용을 그대로 B의 증거로 삼기는 어렵습니다.

**‘검토 완료’ 옆에는 어떤 버전을 봤는지도 중요해요.** 잘 고쳤다는 말의 길이보다 그 말이 가리키는 코드와 확인 항목이 일치하는지가 판단에 도움이 됩니다.

그래서 변경이 추가됐다면 새 버전에서 영향을 받은 항목을 다시 살펴보는 것이 실용적인 운영 방법입니다. 이 권고를 ‘모든 후속 커밋을 제품이 자동 재검토한다’거나 ‘과거 승인이 자동 무효화된다’는 보장으로 읽어서는 안 돼요.

앞의 버튼 예시라면 결과가 한 번 표시되는지, 유지하라고 한 로그인·결제 부분에 관계없는 변경이 들어갔는지 살펴볼 수 있습니다. 확인하지 않은 부분은 확인했다고 적지 않으면 됩니다.

이렇게 하면 AI에게 작업을 다시 맡길 때도 요청이 구체적입니다. ‘다시 잘 고쳐’ 대신 ‘현재 버전에서 한 번 클릭이 두 번 처리되는 부분을 확인해 줘’처럼 남은 문제를 가리킬 수 있죠.

## 3. 역할을 나누어도 마지막 판단은 남아 있어요 🤝

Agent Canvas의 프로필은 역할에 따라 도구·MCP 연결·시크릿을 구성하는 방식을 제공합니다. MCP는 외부 도구와 연결하는 방식, 시크릿은 접근에 쓰는 비밀 값이라고 이해하면 돼요.

문제를 분류하는 역할, 코드를 수정하는 역할, 결과를 검토하는 역할이 모두 같은 도구를 필요로 하는 것은 아닙니다. 공식 글은 이런 작업 구분을 바탕으로 흐름을 구성하는 모습을 설명해요.

또 대화별 전용 Docker 실행 환경을 다룹니다. Docker는 프로그램을 별도 컨테이너 환경에서 실행하는 기술이에요. ‘분리된 환경이 있다’는 설명을 어떤 연결에서도 완벽하게 격리되거나 안전이 보장된다는 말로 바꾸지는 않겠습니다.

여러 단계를 연결해도 수정안을 프로젝트에 합치거나 사용자에게 공개하는 판단이 자동으로 끝났다는 뜻은 아닙니다. 검토할 범위와 유지 관리자가 해야 할 다음 행동이 남아 있어요.

**AI의 완료 보고를 사람이 판단할 수 있는 증거로 연결하세요.** 어떤 문제를 다뤘는지, 어느 버전인지, 확인된 항목과 남은 항목이 무엇인지가 드러나면 다음 결정을 하기 편해집니다.

요청이 자주 오가는 작은 프로젝트나 반복되는 오류 수정에서 이런 흐름을 검토해 볼 만합니다. 반면 문제 자체가 아직 불분명하다면 에이전트 수부터 늘리기보다, 재현되는 상황과 원하는 결과를 먼저 정리하는 편이 좋아요.

오늘 해볼 행동은 최근 수정 제안 하나에 ‘원래 요청 / 완료 기준 / 현재 버전 / 확인한 결과’를 짧게 남기는 것입니다. 기록이 길어야 하는 것은 아니에요. 다음 사람이 같은 버전을 보고 판단할 수 있으면 됩니다.
