## 주제·원문·작성 순서

휴대폰 교체 때 흔히 생기는 ‘대화 백업을 하면 사진까지 옮겨지는가’라는 대중적인 IT 질문을 선택했다. 실제 검색량·미래 트래픽·체류시간 수치를 측정했다는 뜻은 아니다. 최근24시간 주제 신선도 조건은 최신 목표에서 제거됐고, 작성·미디어 생성 전에 공식 상세 본문을 읽었다.

웹 검색은 비공식 유사 도메인을 포함했고 공식 고객센터 페이지의 web 읽기도 실패했다. 비공식 안내를 근거로 쓰지 않고, Chrome에서 `cs.kakao.com` 고객센터의 실제 검색 UI를 이용했다. 공식 상세 도움말 두 개의 읽을 수 있는 전체 본문을 저장했다.

- [대화를 백업하고 복원하려면 어떻게 해야 하나요?](https://cs.kakao.com/helps_html/1073209313): 현재 `더보기 → 설정 → 백업 → 대화 임시 백업` 경로, 무료 텍스트 백업·제외 항목, 비밀번호, 기존 카카오계정 복원, 톡클라우드 과거 데이터 백업 조건.
- [대화를 복원할 수 있는 기한이 있나요?](https://cs.kakao.com/helps_html/1073209323): 무료 백업은 완료 시점부터14일 이내, 앱의 유효기간 확인, 톡클라우드와의 차이.

무료 백업은 사진·동영상·첨부 파일,4,000자 이상 메시지,비밀채팅·오픈채팅을 제외한다. 잊은 백업 비밀번호는 찾을 수 없고 기존 계정으로 복원해야 한다. 톡클라우드 시작만으로 구독 전 자료가 포함되는 것으로 설명하지 않았다. 이 핵심 조건을 수집한 원문과 한 번 대조하고 정확한 본문·미디어 해시에 최종 체크를 묶었다. 사진을 따로 챙기고 저장 장소에서 열어보는 개인 점검은 원문을 복제한 문장 대신 독자의 실제 준비 순서로 구성했다.

관리 화면의 `카카오톡` 검색은 로딩 종료 후2건이었다. 2020년 새해 카드와2019년 카카오택시 글이며 이번 백업 질문의 중복이 아니었다. 공식 버튼2개와 [post193 PC 백업·전환 글](https://nedamma.tistory.com/193)을 연결했다. 각 고유 URL은 한 번만 사용했다.

## 새 미디어와 디자인

직전5편(post189~193)의 장면·표지 기록을 비교했다. 적합한 공식 사진의 재사용 권리를 확보하지 못해 새로운 맥락 사진 두 장과 별도 표지를 네이티브 `image_gen`으로 각각 생성했다. 서로 독립된 세 생성 요청을 함께 실행했다. 도구 원본 세 PNG를 그대로 프로젝트의 무시된 디렉터리에 복사하고, 크기·압축 파생 JPEG만 만들었다. 새 UUID와 정확한 원본 SHA-256의 immutable handoff를 한 번 작성했다.

| 순서 | 파일 | 대체 텍스트 |
|---|---|---|
| 1 · 대표 | `thumbnail.jpg` | 카카오톡 대화 백업과 사진 별도 보관을 표현한 코럴색과 보라색 휴대폰 표지 |
| 2 | `body-photo-1.jpg` | 한국 가정에서 기존 휴대전화 설정을 함께 살펴보는 할아버지와 손자 |
| 3 | `body-photo-2.jpg` | 한국 아파트 주방에서 여행 사진을 살펴보며 휴대전화 교체를 준비하는 모녀 |
| 4 | `workflow.gif` | 기존 폰 대화 백업과 사진 별도 보관 후 같은 계정으로 복원하는 연속 모션 |

표지는 post193의 민트·차콜 노트북 대신 코럴·보라 휴대폰·사진 타일과 큰 한글 제목을 사용한다. 큰 문자는 이미지 생성에서 직접 포함했다. 본문 인물은 조부·손자, 모녀이며 한국 가정의 낮은 탁자·주방에서 실제 준비 행동을 다르게 구성했다. 이전 노트북 장면이나 자산을 재사용하지 않았다.

GIF는 **120프레임,12초,1000×600,무한 반복**이다. 기존 폰과 새 폰, 별도 사진 보관함이 계속 화면에 남고 백업 막대·저장 타일·복원 데이터·포인터가 움직인다. 텍스트 복원과 사진 별도 보관 경로를 나눠 무료 백업이 사진을 자동 전송한다고 오해하지 않게 했다. 장면을 넘기는 슬라이드 방식은 아니다. 실제 카카오 UI·로그인·가입·계정 변경을 수행한 것이 아니라 글의 절차를 설명하는 원본 모션이다.

원문·최종 프롬프트 세트·원본·파생 이미지·GIF 스크립트·체크·저널·공개 화면은 `.artifacts/manual-20261005-kakaotalk-backup-01/`에 보존한다. 미디어나 서명된 이미지 URL은 Git에 넣지 않는다.

## 직접 입력·저장·공개 확인

`티스토리 게시봇` Chrome의 새 글 편집기 한 개를 만들었다. 처음에11:02의 기존 자동저장 글 복원 안내가 떠서 **취소**하고 제목과 본문이 빈 새 편집기임을 확인했다. 이미 공개한 post193을 새 글로 복원하지 않았다.

정확한 HTML을 browser clipboard의 `text/html`과 실제 기본 편집기 붙여넣기로 넣었다. `<td><b>` 표 머리글과 전체 노란 요약 래퍼를 유지했다. 네 파일은 native 사진 버튼 → 미리 등록한 `filechooser` → 정확한 파일 `setFiles` 순서로 한 번씩 첨부했고, native alt 입력과 해당 마커 삭제를 수행했다.

한 번의 최종 편집기 체크에서2,923자,표 머리글,전체 `#fff2bd` 요약 배경,네 이미지 순서·alt,고유 링크3개,마커0개,보이는 캡션0개,삽입 영상0개를 확인했다. 공개·현재 발행·IT 인터넷 홈주제 설정 뒤 최종 공개 발행을 **한 번** 클릭했다. 관리 화면에 새 제목과11:31이 나타났고 공개 페이지 수정 링크가 `/manage/post/194`를 가리켰다.

공개 확인에서 제목·요약·링크·사진3장·대표 썸네일 일치를 확인했다. 초기 빠른 PageDown 반복은 높이649px 화면에서 GIF 구간까지 도달하지 못해 GIF가 `complete=false`,자연 크기0이었다. 이 결과를 성공으로 간주하지 않았다. 실제 위치에 맞춘 native 스크롤 후 GIF가 `complete=true`,**1000×600**으로 로드됐다. 재업로드·재저장·페이지 재생성은 없었다.

익명 조회 한 번은 `/194`에 **HTTP200**,정확한 제목,네 alt,마커0개,UTF-8 대체 문자0개를 확인했다. 결과 화면은 `public-post194.jpg`다. 전체 사이트·외부 광고·픽셀·라이트박스·인쇄 감사는 수행하지 않았다. 모든 요청 조건은 실제 새 글·현재 원문·새 자산·공개 증거로 충족했다.

## 다음 시도에 적용할 점

1. 새로 시작한 목표와 이전 완료 글을 구분한다. 새 글 목표는 새 글로 완료하며 기존 결과 재점검으로 축소하지 않는다.
2. 유사 공식 도메인과 검색 요약은 원문 근거가 아니다. 고객센터 web 읽기가 실패해도 연결된 Chrome의 공식 검색·상세 본문을 먼저 확인한다. 검색 링크가 새 탭으로 열리면 새 상세 탭을 확인해 저장한다.
3. 새 글의 이전 자동저장 복원 안내는 취소 후 빈 상태를 확인한다. 완료 글을 새 글로 복원하지 않는다.
4. 저장 전 사실·편집을 한 번 확인하고 최종 저장 한 번을 지킨다. 구체적인 로딩 미완료에만 해당 자산을 확인한다. PageDown 반복을 로딩 증거로 삼지 말고 실제 위치와 자연 크기로 판단한다.
5. AX/DOM 출력은 **각 항목을 먼저 잘라내고 전체 출력도 제한**한다. iframe 이름에 전체 HTML이 포함될 수 있어 원문 DOM 행을 그대로 출력하지 않는다. 이번 관찰에서 긴 iframe 행이 출력된 점을 다음 실행의 제한 사항으로 기록한다.

이 완료는 수동 보조 게시 성공이며 자동 운영 인증은 아니다. 예약·일일 스케줄은 계속 중지 상태다.
