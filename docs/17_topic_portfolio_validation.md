### 앞선 포트폴리오 가설과 선정 기준

첫 공략 가설은 **디지털 생활에서 원인을 구분하지 못해 막히는 문제**다. AI라는 제품군이나 과거 블로그 스타일로 제한하지 않는다. 큰 검색어를 쫓기보다 독자가 자기 상황을 판별하고 다음 행동을 고를 수 있는 질문부터 시험한다.

저장공간·구독 청구·여행 eSIM은 보존할 후보지만, 기존 조사 순서는 시기성 조건 추가로 잠정 해제한다. 세 후보 모두 현재 관심 상승이나 임박한 사건과의 연결이 미확인이다. 새로운 시기성 후보를 함께 발굴한 뒤 재정렬하며 이 세 주제 안에서만 고르지 않는다. 전 세계 최고 유입의 시장을 발견했다는 뜻이 아니다. 현재 실행 언어는 한국어이며 다른 언어 확장은 별도 검증 대상이다.

단순 ‘iCloud와 기기 용량의 차이’와 ‘구독 취소 방법’은 공식 도움말이 이미 직접 답한다. 이를 번역·재서술하는 글은 우선 제작하지 않는다. 상황별 진단 방식조차 기존 결과보다 유용하지 않으면 해당 후보를 버린다.

## 다음 검증: 사전에 고정할 판정 기준

### 0. 시기적 트렌디함: 왜 지금인가

이번 우선 공략 선정은 **수요 + 시기성 + 독자 가치/차별성 + 검증 가능성**을 함께 충족해야 한다. 시기성은 보너스 점수가 아니라 별도 필수 판정이다. 기존의 품질·권한·안전 조건을 대체하지 않는다.

| 시기성 유형 | 필요한 관측 | 피해야 할 오판 |
| --- | --- | --- |
| 실제 관심 상승 | 같은 조건의 최근 7일/이전 7일, 최근 28일/이전 28일 등 비교 가능한 검색 추이와 관측 시각 | 작은 기준값에서 나온 큰 상승률을 대규모 수요로 표현하거나 뉴스 개수를 검색량으로 간주 |
| 예정된 계절·행사 | 공식 일정·적용 대상, 가능하면 과거 동기간의 수요 패턴과 올해 조건 | 일정이 가깝다는 이유만으로 검색 급증이 이미 관측되었다고 주장 |
| 출시·업데이트·제도 변경 | 최신 공식 발표, 발표일과 실제 시행일, 그 변화로 새로 생긴 구체적인 독자 질문 | 문서 수정일만 새롭거나 오래된 글 제목에 연도를 붙인 것을 트렌드로 처리 |

후보마다 `why_now`, `trend_type`, `evidence_urls`, `observed_at`, `event_at`(해당 시), `comparison_window`, `momentum`(상승/정체/하락/UNKNOWN), `opportunity_window`, `publish_by`, `recheck_at`, `expiry_action`을 기록한다. 이는 편집 기록 규격이며 아직 런타임 스키마에 구현된 필드는 아니다.

- 관측된 관심 상승과 예정된 관심의 가설을 구분한다. 공식 사건과 직접 연결된 독자 문제가 확인되면 선제 검토할 수 있지만 수요는 예측으로 표기하고, 새 이슈에 존재하지 않는 3개월 이력을 요구하지 않는다.
- 작성·검수·승인 및 검색 노출까지의 시간을 고려해 유효한 기회 기간에 전달 가능한지 확인한다. 색인 소요시간은 UNKNOWN이며 즉시 노출을 전제하지 않는다. 기회가 너무 짧으면 우선순위를 내린다.
- 시점 근거가 없으면 `timing_gate=PENDING`으로 두고 이번 우선 제작 큐에는 넣지 않는다. 상시 수요 후보는 폐기하지 않고 후순위 자산으로 보존한다.
- 사건 취소·조건 변경·관심 하락·기회 만료 시 재평가한다. 만료된 후보는 신규 제작 중단, 기존 글은 갱신 검토로 전환한다. 실제 게시물 수정·삭제는 별도 승인 경계를 유지한다.
- 현 단계에서 새 실시간 트렌드 데이터는 수집하지 않았다. 기존 TP-01~06에 시기성 통과 판정을 부여하지 않는다. 특정 신제품 출시나 휴일을 근거 없이 기존 후보에 끼워 맞추지 않는다.

### 1. 수요 관측

- 한국 대상, 완료된 동일 기간 2025-09-01~2026-08-31의 월별 추이와 2026-06-09~2026-09-06의 주별 추이를 별도로 비교한다. 미완료 월을 완결 월처럼 해석하지 않는다.
- TP-01~03 및 기존 TP-04~05의 질의 묶음을 비교하되 브랜드 전체 관심과 특정 문제 관심을 분리한다. 묶음 정의와 필터를 결과와 함께 보존한다.
- 공개 데이터랩/Trends 화면에서 허용된 조회와 내보내기를 우선한다. 인증·보호·권한 문제가 생기면 중단하고 누락을 표시한다. 신규 API 등록·유료 키워드 서비스는 승인 없이 사용하지 않는다.
- 상대 추이를 월간 검색 횟수로 환산하지 않는다. 서로 다른 조회의 100을 같은 규모로 비교하지 않는다. 공통 기준어를 쓰더라도 조회 조건과 정규화 한계를 유지한다. 데이터 없음은 수요 0이 아니다.
- 상시 수요의 임시 통과 기준: 질의 묶음이 최근 3개월 모두 관측 가능하고, 독립적인 실제 문제 표현을 서로 다른 출처 2곳 이상에서 확인할 것. 신규·시기성 이슈는 가용한 최근 비교 구간과 독립적인 문제 표현을 사용하며 3개월 이력을 일괄 요구하지 않는다. 예정 사건은 공식 일정과 직접적인 독자 필요를 근거로 선제 실험을 검토하되 수요는 HYPOTHESIS로 유지한다. 모두 자원 배분 가설 기준이지 성과 보장이 아니며 자료 부족을 숫자 추정으로 보완하지 않는다.

현재 이 추이 조회 및 2곳 교차 확인은 **미실행/미완료**다. TP-01~03 모두 demand_gate=PENDING이다.

### 2. 경쟁과 독자 가치

- 수요 게이트가 열리는 후보부터 한국어 실제 검색 결과를 동일 조건에서 최대 10개씩 확인한다. 엔진·일시·기기·질의·URL을 보존하고 광고/쇼핑/영상/공식 문서를 구분한다. 개인화/지역 차이를 한계로 기록한다.
- 각 본문이 질문에 답하는지, 예외 조건·실패 시 다음 경로·손실 위험을 다루는지 기록한다. 검색 스니펫만으로 누락 판정 금지.
- 임시 통과 기준: 상위 결과들이 놓친 중요한 판단 분기 1개 이상을 특정하고, 이를 공식 근거 또는 실제로 수행한 재현으로 설명할 수 있을 것. 기존 우수 자료가 이미 해결하면 기각하거나 공식 링크만 추천한다.
- 브리프를 먼저 만들고 사실/가상 예시/미실행 실험을 분리한다. TP-01은 사진 삭제나 계정 변경 없이 판별 가능해야 하며, TP-02는 영수증·계정·카드 원문을 수집하지 않는 안내여야 한다.

현재 gap_gate=PENDING, 실사용 테스트 없음. 이를 통과하기 전 새 완성 원고 묶음이나 승인 패키지를 만들지 않는다.

### 3. 작게 실행하고 폐기할 수 있는 포트폴리오

- 기존 TP-01 우선 순서는 해제한다. 시기적 신호로 새 후보를 발굴하고 기존 TP-01~06과 함께 검토한다. 수요의 근거 수준, 남은 기회 기간, 경쟁 공백, 검증 가능성을 비교해 첫 상세 검증 대상을 다시 고른다. 동시에 여러 글을 제작하라는 지시가 아니다.
- 검증 통과 후보 1개만 브리프→조사→초안으로 이동한다. 실패하면 이유를 기록하고 다음 후보로 넘어간다. 기존 제미나이 작업의 매몰비용으로 주제를 고르지 않는다.
- 공개 발행과 분석 접근은 별도 승인 후 가능하다. 허용된 경우 동일 관측 창에서 색인 여부, 질의별 노출·클릭, 글당 비용/갱신 시간을 수집한다. 비공개 글이나 인위적 방문으로 검색 성과를 시험하지 않는다.
- 처음에는 주간 진단, 28일·56일 누적 관측을 제안한다. 이는 잠정 점검 시점이지 그 기간 안에 성과가 보장되거나 완전히 판정된다는 뜻이 아니다. 색인·계측 문제를 콘텐츠 수요 실패와 구분한다.
- 세 후보의 클릭 몇 건으로 승자를 선언하지 않는다. 표본이 작으면 판정 유보; 노출은 있으나 클릭이 약하면 제목/의도 일치 가설, 클릭 후 질문이 해결되지 않으면 본문 가설을 한 번에 하나씩 시험한다. 기준선 없이 목표 CTR/RPM을 꾸미지 않는다.

## 완료된 것 / 남은 것

완료: 6분야 초기 선별, 6개 의도 묶음, 3개 우선 조사 후보, 공식 대체재 확인, 순위 주장의 반증, 게이트와 중단 조건 정의.

미완료: 동일 조건 실제 추이, 대표 검색 결과 본문 비교, 입증된 콘텐츠 공백, 실제 기기/독자 테스트, 새 글 작성·게시·성과. 따라서 ‘주제 발굴 1차 선별 완료’까지만 주장한다.

다음 가장 작은 작업: 최근 관심 변화·다가오는 일정·공식 변경 발표에서 ‘왜 지금인가’가 있는 후보를 찾아 기존 후보와 재비교한다. 기술적 도움말을 더 쌓는 것만으로 시장 검증을 대신하지 않는다. 별도 제작 도구·대규모 에이전트·문서 포맷·기기 설정 작업은 이 우선순위에 필요하지 않다.
