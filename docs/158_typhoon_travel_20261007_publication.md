## 서식 확인과 원인

사용자가 제시한 기준은 `1. 제목` 한 줄만 크고 굵게 표시하고, 그 뒤 문단은 일반 크기·굵기로 유지하는 것이다. 공개된 post211에서 검증된 대응값은 제목 23px/700, 본문 16px/400이다.

2026-10-07 편집기 접근성 트리에서 다섯 번호 제목과 일반 문단 모두 같은 일반 텍스트 요소로 보였다. 즉 제목 스타일은 아직 적용되지 않았다. 로컬 Markdown 초안은 다섯 제목을 `##`로 구분하지만, 작성기에 붙여 넣은 본문은 일반 텍스트로 전송되어 그 Markdown 제목 구문이 네이티브 제목 서식으로 변환되지 않았다. 작성기에는 임시 표식도 남아 있어 이 상태는 완료본이 아니다.

HTML 모드로 전환하려다 티스토리의 “현재 서식이 유지되지 않을 수 있다” 확인창을 받았다. 확인 버튼 조작 시도에서 CDP 포커스 제어 시간 초과가 발생했고, 이후 같은 작성기 상태를 읽지 못했다. 확인창 처리 완료와 모드 전환 완료는 모두 미확인이다.

## 원인 재현과 재발방지 수정 — 2026-10-07

### 관찰로 확인한 장애 경계

원본 세션 `rollout-2026-10-06T18-14-17-01a1107e-0797-71b0-af3f-83c510da3a10.jsonl`의 21775·21782줄은 실제 모드 변경 JavaScript confirm을 보여 준다. 21786→21789줄의 확인 버튼/AX 호출 묶음부터 `Emulation.setFocusEmulationEnabled` 시간초과가 발생했다. 어느 문장에서 처음 실패했는지는 그 묶음만으로 분리할 수 없다. 같은 프로필의 신규 관리자는 정상 응답하고 동일 작성기 재바인딩은 실패했다. 단순 로그인 만료나 프로필 전체 연결 손실은 이 탭별 현상을 설명하지 못한다.

현재 설치된 `@oai/browser-desktop/scripts/browser-service.mjs`의 정적 경로를 읽었다. `ensureAttachedTab`은 `api.attach` 다음 `enableFocusEmulation`을 기다린 뒤 `Page.enable`을 포함한 attach handlers를 실행한다. `executeTargetCdp`는 실제 명령 전에 이 초기화를 기다린다. 따라서 확인창 처리와 `closeTab`도 포커스 초기화에서 실패하면 실제 처리/닫기 명령에 도달하지 못한다. `getJsDialog`는 `jsDialogsByTabId` 메모리 캐시를 읽으므로 `undefined`만으로 실제 브라우저의 확인창 부재를 증명할 수 없다. 설치 앱 코드는 변경하지 않았다.

같은 게시 프로필의 로컬 테스트 페이지(블로그·계정 정보 없음)에서 동일한 confirm 문구와 버튼으로 재현했다:

- 실패 경로, 탭 `959319030`: 클릭을 먼저 `await` → `Input.dispatchMouseEvent` 2965ms 시간초과 → `getJsDialog`가 `confirm` 반환 → 뒤늦은 `dismiss`도 `Emulation.setFocusEmulationEnabled` 10000ms 시간초과.
- 기존 작성기에 대해 CUA REPL을 재설정하고 동일 확장 식별자로 새 연결을 만들었지만, `getJsDialog`는 `undefined`, DOM 읽기는 동일 포커스 시간초과였다. 숫자 브라우저 ID는 1→2로 바뀌어 고정 확장 식별자로 연결했다.
- 현재 로컬 호스트의 읽기 전용 OS 검사에는 `IOConsoleLocked=Yes`, `CGSSessionScreenIsLocked=Yes`가 있었다. 이는 현재 네이티브 제어 불가에 관한 별도 근거다. 이전 사용자 화면이나 기존 작성기의 탭별 CDP 장애를 실제 Mac 잠금으로 바꾸어 설명하지 않는다.

**확인창을 띄우는 클릭의 응답을 먼저 기다리면 명령이 시간초과되고, 이후 포커스 초기화가 확인창 처리를 가로막는 실패 순서**를 Tistory 밖에서도 재현했다. 원래 작성기의 현재 확인창 내용과 브라우저 확장 내부에서 연결 상태가 무효화되는 상세 원인은 아직 직접 관찰하지 못했다.

### 성공 경로 — 확인창 즉시 처리

- 태그: `성공 경로`
